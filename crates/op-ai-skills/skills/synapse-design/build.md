# OP Engine Build Guide

Mandatory construction rules for Synapse high-fidelity canvas design. User requirements and the selected product `DESIGN` supply all visual identity (palette, typography scale, corner radii, surface tokens, elevation); this guide governs how to translate that design into valid, non-overflowing, editable OP nodes.

## 1. Progressive Skeleton & Canvas Contract

- **Use the host's seeded root when present:** In a DSH private draft, `synapse_design_pipeline_begin` seeds one page root (`rootNodeId`) at the authoritative width (`1440` web, `390` mobile). Build inside `rootNodeId`; never insert a second top-level page root for the first screen.
- **Additional screens open to the right:** For multi-screen designs on an open canvas or additional boards, place each new top-level screen frame to the right (`find_empty_space` with direction `"right"`), never stacked vertically below an existing screen.
- **Batch 1 — Skeleton shells:** Create named top-level section shells in reading order with temporary numeric heights so structure is immediately visible (empty `fit_content` shells collapse to `0`). Fill one major section per subsequent batch (`<= 25` operations per batch) and switch completed content shells to `height: "fit_content"`.
- **Final sizing invariant:** Content-bearing sections, cards, lists, and ordinary wrappers default to `height: "fit_content"` (Hug). Use `height: "fill_container"` only for one designated remainder consumer under a definite-height parent (such as a main work pane or clipped scroll body) or cross-axis stretch inside a fixed-height horizontal row. Never switch sibling cards to `fill_container` height merely to hide unequal copy. Complete fluid roots at `height: "fit_content"`; preserve explicit numeric root height only when `fixedViewport` is true or the user requested a fixed viewport/app shell.
- **Act on `layoutIssues` immediately & preserve working state:** Inspect batch receipts before continuing. Repair reported overflow or collapsed containers with targeted updates before building the next section. Never delete a working section in one call and rebuild it later; replace and remove stale nodes in a single transactional batch.

## 2. Auto-Layout, Z-Order & Row Math

- **Explicit layout mode:** Every container frame with flow children must declare `layout: "vertical"` or `layout: "horizontal"`. Never set `x` or `y` on children inside flow containers.
- **Deliberate absolute stacks (`layout: "none"`):** Every child inside a `layout: "none"` container requires explicit numeric `x`, `y`, `width`, and `height` (`fill_container` has no meaning without a flex parent). Children render front-to-back by array index (`children[0]` paints topmost); place badges, labels, controls, and scrims before background media.
- **Horizontal row width math:** Fixed-width items in a horizontal row do not shrink automatically; verify `N * item_width + (N - 1) * gap <= parent_width - padding_left - padding_right` so trailing items never clip off-canvas. Use `width: "fill_container"` for flexible columns (`flex-1` behavior).
- **Transparent structural wrappers:** Keep structural layout wrappers (`Header`, section rails, column groups) transparent (`fill: []`) so they inherit the page surface; apply surface fills only to intentional cards, sidebars, toolbars, inputs, and controls. Set `clipContent: true` on rounded containers holding edge-to-edge media, and keep nested radii concentric (`R_inner = max(4, R_outer - padding)`). Note that the current layout adapter does not enforce `minWidth` or `minHeight` as hard layout constraints; verify actual measured bounds.
- **Dropdown & select chevron inset:** Frame-built select/dropdown triggers (`layout: "horizontal"`, `alignItems: "center"`, `justifyContent: "space_between"`) must declare `padding: [0, 12]` to `[0, 16]` (never `0` or `< 8px`, which glues the `chevron-down` icon against the right border) plus `gap: 8`–`12`, with flexible or wide-enough label space (`width: "fill_container"` / `textGrowth: "fixed-width"` or generous trigger width) so text never collides with the trailing chevron. Native `{type: "select"}` controls must likewise be wide enough for the longest visible label plus a `40px` trailing chevron zone.

## 3. Text Sizing, Overflow & CJK Typography

- **Paragraphs & multi-line copy in vertical layout:** Set `width: "fill_container"` with `textGrowth: "fixed-width"` so text wraps cleanly and grows vertically. Never hardcode fixed pixel widths on text inside layout frames or fixed pixel heights on cards that hold text plus actions.
- **Short labels in horizontal rows:** Set `width: "fit_content"` with `textGrowth: "auto"` on buttons, badges, tabs, and inline metadata so labels never squeeze or wrap into 1-character columns.
- **CJK typography & language consistency:** When the user's request is in Chinese, Japanese, or Korean, write every UI string in that language (navigation, buttons, table headers, placeholders, status badges, empty states), keeping only true brand/code proper nouns in Latin. Use `"Noto Sans SC"` (Chinese), `"Noto Sans JP"` (Japanese), or `"Noto Sans KR"` (Korean) for headings when the selected `DESIGN` names a Latin-only display font that lacks CJK glyphs.
- **CJK metrics & punctuation:** Size-band `lineHeight` (`>= 64px`: `1.02–1.15`, `48–63px`: `1.15–1.25`, `40–47px`: `1.3–1.4`, body: `1.7–1.8`, captions: `1.45–1.5`). `letterSpacing` is absolute `px`: keep `0` below `48px` (never negative tracking on CJK body/UI text, and `0` on CJK tags even when styled like Latin micro-labels). Size CJK buttons so `width >= charCount * fontSize + horizontal_padding`, keep reading lines `<= 30` Han characters, insert one space between CJK and inline Latin/digits (none before `%` or units), never truncate CJK titles with ellipses, and avoid closing punctuation at line start or opening punctuation at line end.

## 4. Variables, Components, Icons & Realistic Density

- **Single token source of truth:** Inspect existing document variables first (`get_variables`) and bind `"$variableName"` references instead of raw literals where matching semantic tokens exist. When Talkdesk Cobalt is the active style, reference Cobalt library variables directly (`$--surface-elevation-0`, `$--surface-elevation-1`, `$--text-default`, `$--text-description`, `$--primary-9`, `$--primary-contrast`, `$--secondary-5`, `$--secondary-12`, `$--gray-6`, `$--border-focus-color`, `$--spacing-small`, `$--spacing-medium`); they import with aliases on first use.
- **Preset token disambiguation:** In shadcn-vocabulary documents (`$--background`, `$--foreground`, `$--card`, `$--primary`, `$--primary-foreground`, `$--muted`, `$--muted-foreground`, `$--border`), `$--accent` is a neutral hover surface, never the brand color. Only reference variables confirmed by `get_variables` or `list_library_variables`.
- **True linked component reuse:** Before building repeated rows, cards, nav items, or controls that share structure and semantics, inspect existing components; otherwise author one master frame (`create_component` in direct MCP, or `reusable: true` with `previewAsScreen: false` on a non-screen master in `synapse_design_pipeline_batch`) and instantiate linked `{type: "ref", ref: "<masterId>"}` nodes. Read back the master's actual descendant IDs before passing `descendants: {"<childId>": {...}}` overrides or `set_instance_properties`. `instantiate_component` and `C()` create independent copies and do not count as linked reuse.
- **Icons, vectors, rings & sensitive inputs:** Author UI icons as `{type: "icon_font", iconFontName: "<glyph-name>", width: 18, height: 18, fill: "..."}` where `iconFontName` is the glyph identifier (`"search"`, `"plus"`, `"settings"`, `"message-square"`), never the font family (`"lucide"`) and never emoji characters. Author gauges/rings with `role: "progress-ring"` and `ellipse` (`innerRadius`, `startAngle`, `sweepAngle`) inside a fixed square `layout: "none"` wrapper (center label -> progress arc -> track). On password, secret, or masked `text_input` controls in any language, always set `secure: true` and `role: "password"`. Create raster image slots only when the domain genuinely calls for photography or avatars, never as filler on operational or text-first surfaces.
- **Populated product density:** Operational tables and entity lists must include at least `6` realistic, varied rows (distinct names, statuses, timestamps, metrics) plus complete surrounding workspace context (filters/search, primary action, summary or detail zone), with tables structured strictly as `Table frame -> Row frame -> Cell frame -> Cell content`.
