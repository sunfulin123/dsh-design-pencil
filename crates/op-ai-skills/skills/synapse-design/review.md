# OP quality review

Review is evidence-led acceptance, not a description of the design. Each conclusion is tied to something that was actually examined, and anything not examined is reported as `unverified` (statuses and evidence are defined in `op-design-judgement`, section 6).

## Method

1. **Completeness before appearance.** First confirm that the expected content, components, states and primary actions exist and are visible: compare planned content, node content and the rendered screenshot. Only then judge spacing and visual quality. A gap left by blank text, an empty component, an instance override that did not apply or an unloaded asset is missing content, not whitespace, and adjusting spacing around it does not fix it.
2. **Three scales, all on the real render.**
   - *Whole screen:* task completeness, information architecture, visual centre of gravity, reading order.
   - *Groups:* sibling consistency (same heading indent, same heading-to-content distance, same row anatomy), which content belongs to which group, rhythm between and within groups.
   - *Details:* inset from content to its container edge (badges, counters, corner controls), baselines, optical centring, clipping and overlap.
   Looking only at the whole screenshot misses detail defects; looking only at the edited node misses what the edit did to its surroundings.
3. **Change of role.** Walk the primary task as the user. Then ask what a senior designer would point at first. Order the findings by severity and repair from the top.
4. **Diagnostics are leads.** No finding does not mean pass, and a finding does not mean the suggested change is right; weigh each against the render and the intent. A centring measurement of one text line against its whole container is not a reason to move a line of a multi-line title.
5. **Depth matches the change.** A new design gets the full review. A local edit checks the target, its siblings, its parent, the adjacent regions and every affected component instance.
6. **Scope fidelity + design upgrade.** When a confirmed prototype or reference exists, preserve its confirmed scope (screen list, state coverage, copy/core flow, and verifiable actions) while upgrading visual hierarchy, typography, spacing, and component craft (`deviation: "upgrade"` + `designUpgrades: [{what, why}]`, no user approval needed). Dropping a screen or shell, changing how a state is expressed, or reducing copy/actions is a `substantive` scope deviation that requires user confirmation before delivery. When one screen's states are built as multiple independent frames, list all of those frame IDs together under `nodeIds` on that single screen entry rather than duplicating the screen name. If the same review diagnostic class recurs twice in a row, stop and ask the user instead of submitting another approximate receipt.

## Tools

Inspect the relevant node hierarchy and measured layout, then examine a real rendered screenshot. Confirm that the capture shows the intended board and is not empty or stale before judging it. Scope screenshots and diagnostics to the requested design or local edit. An approximate preview is not exact canvas evidence.

Call `lint_document` scoped to each changed screen, inspect totals and follow `nextCursor` until relevant findings are reviewed. A `get_design_quality` page alone may omit findings. For a DSH private draft call `synapse_design_pipeline_context` with `{draftId, tool:"lint_document", arguments:{rootId, limit:50}}`; pass `value.nextCursor` as `arguments.cursor` with the same scope and filters. Compare a candidate with its siblings, visible content, semantic role, state, layout and selected DESIGN; classify it as confirmed, intentional/false positive, or indeterminate. Group repeated reports by cause. Depth alone does not justify removing a node or wrapper; preserve meaningful table columns, layout and content. `autoFixEligible:false` requires an explicit design decision even when severity is warning. For a confirmed problem edit only the affected nodes, then relint from the first page, read back and inspect a fresh CanvasKit screenshot. Do not use a bulk fix to normalize intentional variants.

Report one check per rubric dimension with a status (`pass`, `fail`, `unverified`, `not-applicable`), the inspected `nodeIds`, the executed `method` and what was not covered:

1. **`task_integrity`:** every planned screen (each in its own non-empty container frame) and primary action is present and visible; no unrelated content was replaced; POC screens are compared against their recorded captures; each primary action is classified `verifiable`, `visual-only` or `not-implemented`, and `verifiable` ones are exercised with `simulate_prototype`.
2. **`structure_overflow`:** inspect reported overflow, collapsed containers, text/control clipping, undersized interactive targets across all `touchTargetsNextOffset` pages, and unexpected empty space (check for missing content first). Read back changed nodes instead of assuming a command succeeded.
3. **`hierarchy_density`:** identify the main focal region, reading order, primary action prominence, the three levels of space, and the density tier (`Operate`, `Persuade`, `Read`, `Experience`).
4. **`style_consistency`:** compare typography (including `fontResolution`), palette, surfaces, tokens, readable contrast, sibling consistency and linked `{type: "ref"}` components against the selected DESIGN and existing document. Gradients, opacity, and images can make automated contrast indeterminate; a 44px target heuristic or screenshot does not prove keyboard behavior or full WCAG compliance.
5. **`content_states`:** verify realistic domain copy, UI copy language (English by default unless the user explicitly requested another target UI language, with single-language consistency and CJK typography rules when a CJK UI language was requested), `contentIssues` from `get_design_quality`, and explicit coverage (`designed` with `nodeId` or `not-applicable` with reason) for `loading`, `empty`, `error`, `partial`, `success`, and `permission`. Confirm the exact viewport, renderer, and screenshot version; a capture is not proof that an image-capable model inspected it.

For repeated controls with shared meaning, first discover existing masters. To make a new linked component, promote a suitable frame with `create_component`, expose changing text through `add_component_property` when appropriate, then insert `{type: "ref", ref: "<master node id>"}` under the desired parent using `insert_node` or `batch_design`. Set per-instance values with `set_instance_properties`; read the nodes and visually verify. `instantiate_component` currently creates an independent page-root clone, so it does not provide linked reuse. Keep distinct interactions and local overrides, and do not change a shared master during a local-only edit without authorization. Existing repeated nodes are review candidates, not permission to replace them blindly.

In a private DSH draft, use `synapse_design_pipeline_batch` to author a `reusable:true` frame and linked refs; after reading the master's actual descendant ids, set differing text with ref `descendants` overrides. Use `synapse_design_pipeline_inspect` with `kind:"quality"`, `nodeId`, `limit` and `touchTargetOffset` for scoped, paginated checks; it returns the underlying quality result. Keep screenshot inspection on the draft's screenshot path.

For each changed screen call `get_design_quality` and inspect `navIssues` separately from generic `findings`. The 44px value is a recommendation, with smaller targets ranked first; use the intended device and selected design to decide the remedy. `suggestedPatch` is a proposal, not proof that the hit area fits its parent or remains clickable. If `patchAvailable` is false, inspect constraints and consider a larger interaction wrapper; an instance's `componentId` identifies the shared master but changing it affects other instances. After applying changes, call the quality tool again and inspect the measured geometry and a fresh screenshot. Follow `touchTargetsNextOffset` to inspect further results, restarting at offset 0 after mutations; report remaining or inaccessible targets honestly. Recheck after the last mutation, not just before finalization.

Read `tokenObservations` as limited evidence: an unbound literal that equals a document variable is not necessarily the same semantic token, and a component's local override can be intentional. Preserve it unless the request calls for changing it. Indeterminate values are not violations; compare only against explicit document or selected DESIGN rules. `tokenObservationsTruncated` reports omitted informational observations; `truncated` separately reports omitted diagnostic findings.

Treat automated aesthetic alerts as prompts for context-aware review: an existing brand font, purple accent, compact table or repeated component can be intentional. The selected DESIGN and explicit user instructions outrank generic anti-pattern rules. Never use screenshots or structure-only diagnostics to claim actual user testing.

Treat missing content, unreachable actions, clipping, overlap, overflow and missing key states as blocking; then address legibility, hierarchy and polish. Fix confirmed defects locally and retest the same checks, with a fresh screenshot for visual changes. In a DSH private draft, submit `synapse_design_pipeline_finish` with a structured `review` receipt: `visual.screenshotSha256` of the inspected finalized preview; each planned screen mapped to a distinct non-empty container `nodeId` (or `omittedReason`), with `pocScreenshot`, `deviation` and, for an omitted screen or a `substantive` deviation, `confirmation.questionId` of the user's answer for POC tasks; one `checks` entry per rubric dimension; `actions` classified by delivered capability; all six `states`; and `reuseNote` when reuse candidates remain without linked `{type: "ref"}` instances. A `fail` check stops publication until the defect is repaired and re-checked; an `unverified` check is published and reported to the user as unverified. Structural diagnostics and visual judgment complement one another; neither is a substitute for the other.
