## Start and reuse a local development server

Start the development server yourself using the available shell/process tools. For confirmed Cobalt SS tasks use `synapse_design_prototype` install/check for the prepared project. The install action runs pnpm in the prepared project. Never run `pnpm`, `npm` or `yarn` `install`/`add`/`i` in a shell while that tool is available; a sandboxed shell leaves a `.pnpm-store/` directory that `check` and handoff refuse. If installation fails, report its actual error and keep the same project for retries. Preserve the project dependency and build configuration. Then run `pnpm run dev` in that project through an owned process session. Outside SS, install only in the project and diagnose the actual registry failure before an explicit retry. Read Vite’s actual loopback URL from its output, retain the process handle and wait for a successful HTTP response before browser checks. Vite may choose another port when its default is occupied; use the reported URL without changing or terminating another service. Reuse this process for HMR instead of reinstalling or restarting after each edit. Ordinary HTML can use an existing local HTTP server or an owned server rooted at its task directory.

SS Preview Fill with AI, `.synapse/preview.json` and the SS service list are not prerequisites for POC development. Do not ask the user to configure them or treat an empty service list as a blocker. If the user already has a suitable managed service, it can be reused; do not modify its configuration or stop its process. Keep SS Preview’s static-file handoff for final presentation.

Do not stop after scaffolding. Finish the requested business pages and interactions, install/start the local project and verify them before reporting completion. The review CLI consumes the running URL; it does not install or start the development server. If actual shell execution, package access or permissions are unavailable, report that specific failure and continue independent implementation; never replace the missing capability with repeated requests for Preview setup.

Record the project directory, command, process handle and URL. Stop only processes created for this task, using that handle, when no longer needed; keep a requested review preview available. Never kill by name or port. Report actual installation failures rather than substituting components or claiming startup succeeded.

Background jobs are not durable services across a Harness restart. When resuming, check the recorded process handle and actual URL instead of assuming the server survived. If your task-owned server has stopped, restart it from the recorded directory and command, read its new URL and wait for HTTP readiness; do not reinstall unchanged dependencies or stop somebody else's service.
