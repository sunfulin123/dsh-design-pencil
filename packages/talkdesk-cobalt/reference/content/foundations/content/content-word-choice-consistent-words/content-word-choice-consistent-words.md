# Consistent words

## Guidance

### Avoid saying "sorry"

Use "sorry" only in error messages that result in serious problems for the user (for example, data
loss, the user can't continue to use Talkdesk, or the user must contact Support).

![A generic 'ERROR 504 - Service unavailable' page reading 'We're sorry, our service is temporarily unavailable, but we should be back up shortly. Please contact us if the problem persists.'](/assets/content-word-choice-consistent-words/word-choice-avoid-sorry-do.png)
*Do We should apologize because is Talkdesk is down.*

![A generic Talkdesk sign-in form showing the error 'Sorry, but you must include a symbol in your password'](/assets/content-word-choice-consistent-words/word-choice-avoid-sorry-dont.png)
*Don't The user made a mistake. No need for us to apologize.*

**Note:** Before you use "sorry" in UI text, ask yourself if you could change the design to avoid the
situation.

---

### The use of "please"

Use "please" sparingly and only if an action is really serious and important, or if you're asking the
user to complete a task that is not that easy. Sometimes, an imperative CTA is all that's necessary.

Don't use "please" in the normal course of explaining how to use a product, even if you're explaining a
difficult task.

Use "please" when you're asking for permission or forgiveness—for example, when what you're asking for
benefits us, inconveniences a reader, or suggests a potential issue with a product.

### Using "We" and "You" in messages

#### We - Our product, Talkdesk

Using "we" in messages can:

* Establish a relationship between the user and the product.
* Give the user the idea that the product is working together with them to achieve a shared goal.
  **e.g.** *"We've made some improvements based on your feedback"* can help the user feel like they are
  part of the process.
* Shift the responsibility of something going wrong to us, Talkdesk, when needed. **e.g.** *"We
  apologize for the inconvenience caused"* helps reassure the user that the company is working to fix
  the problem.
* Create a more positive experience and can help celebrate the user's accomplishments, when used in
  success messages. **e.g.** *"We've received your payment and your subscription will be ready soon"*
  is more friendly than *"Payment received"*.
* Help explain why certain actions or information are necessary for the user. **e.g.** "We need your
  location to provide an accurate timezone" is more informative than "Allow us to access your
  location".
* Create excitement and anticipation for the user, when used in Onboarding. **e.g.** *"We want to
  introduce our new feature that allows you to customize your profile"* rather than *"Check out our new
  feature"*.

Other things to take into consideration:

* "We" should be mentioned to refer to our product.
* Do not use "we" to mention both the user and the product.
* Do not overuse "we", as the content/messages can become more self-centered and can create a sense of
  distance between the user and the product.

#### You - The user

Using "you" in messages can:

* Help address the user directly when sending a message or a notification.
* Create a more personalized experience and helps the user feel more engaged with the product.
* Make the user take action, helping create a sense of urgency and encourage the user to take the
  desired action. **e.g.** *"You can now assign users to your seats"*.
* Address the user's needs, creating a more empathetic and user-centric experience. **e.g.** *"Orders
  \#189 and #186 need your attention"*.
* Help soften and create a more supportive experience, when used in error messages. **e.g.** *"Your
  seats couldn't be updated. Please try again or contact Talkdesk"* is more friendly than *"Seats update
  failed"*.
* Engage, when introducing the user to a new feature. **e.g.** Saying *"You're going to take so much
  advantage of our new feature"* instead of *"Check our new feature"*.

Other things to take into consideration:

* Avoid using "you" too much. Just like any word that becomes too much repetitive, can be overwhelming.
  Use "you" sparingly and strategically to avoid overloading the user with too much language.

### View more, show more, see more

#### View more

Can be used when the user is browsing through a list of items and needs to view more names, numbers,
etc from that list;

#### Show more

Can be written when the user is viewing a specific page and needs/wants to see more content;

#### See more

A more generic terminology. Must be written when the user needs to see more options, for example.

### When to "Cancel", "Close", "Reset", and "Clear"

#### Cancel vs Reset

* Use "Cancel" when you want the user to confirm they want to abandon or dismiss an action. **e.g.**
  *"Cancel call!*
* Use "Reset" when you want to give the user the option to revert to the original state of the
  interface. e.g. *"Reset filters"*
* Make sure the "Cancel" button is clearly visible and positioned in a prominent location, such as on
  the bottom right-hand side of the interface.
* Use "Reset" sparingly (compared to "Cancel") and only when it's necessary to give users the option to
  start over from scratch.

#### Cancel vs Close

* Use "Cancel" when the action being taken can be undone or reversed, such as canceling a call, an
  order, or a subscription. **e.g.** *"Cancel call"*
* Use "Close" when the action being taken cannot be reversed, such as closing a window. **e.g.** *"Close
  chat"*

#### Reset vs Clear

* Use "Reset" when you want to give the user the option to revert to the original state of the
  interface. **e.g.** *"Reset filters"*
* Use "Clear" when you want the user to erase any input or selection they have made when filtering or
  to erase their input. **e.g.** *"Clear filters"*
* Make sure the "Reset" and "Clear" buttons are clearly labeled and easy to distinguish from one
  another.

**For all scenarios:**

* Consider using a warning/confirmation message to double-check if the user really wants to cancel or
  reset the action.
* Be consistent with the terms you use across the product to avoid confusing the user.
