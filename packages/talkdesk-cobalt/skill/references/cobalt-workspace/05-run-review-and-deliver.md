## Run, review and deliver

- Start the development server yourself through the available shell/process tools after completing the requested business code. In SS tasks use `synapse_design_prototype` install/check to install dependencies and inspect the prepared project. Report any install error in chat and retry in the same project when requested; then run `pnpm run dev`. Standalone CLI users install only inside their own project, diagnose network/authentication/certificate errors and explicitly retry after restoring access; retain the process handle, read the actual loopback URL from Vite and confirm HTTP readiness before browser validation. Reuse the server for HMR. SS Preview Fill with AI, `.synapse/preview.json` and a configured service list are not prerequisites; do not send the user to configure them or stop at the scaffold because the list is empty. The shared `references/poc-review.md` owns startup, process cleanup and verification. The scaffold selects pnpm 11.7.0; keep its pnpm-workspace.yaml and React 18 baseline, leave legacy peer warnings visible and preserve the esbuild allowance. Private `@talkdesk/*` packages require registry/VPN access; report a real install failure rather than substituting controls. Build static delivery for the existing final POC handoff.
- Each business route consumes `usePrototypeScenario()` from `src/prototype-runtime/scenarios`. Implement Ready, Loading, Empty, Error, Partial and No access with the route's own sample content and action availability. Pass the scenario to recipes that accept it. When a recipe has no scenario prop, handle the states in the route rendering it. State buttons live beside the size controls in the top toolbar.
- BasicTable and list recipes are flush full-width surfaces: no rounded outer card, border, shadow or horizontal table-parent padding. Retain cell padding and row separators. Header, search and form regions own their insets. Use the copied Extensions SidePanel for list details. Verify table edges and every collapsed Dock icon center numerically in default and selected states; expanded Dock icons must align with their labels.
- Begin from the closest recipe's structure and dimensions, then record justified departures. Write explicit layout measurements before coding: content padding, header and toolbar heights, group/row/control gaps, and which controls stay on one row. Inspect actual rendered business frames, including toolbar and pagination child centers, text truncation, overflow and position changes across states. Record numeric measurements and screenshots for each reviewed region; an absence of overflow alone does not establish alignment.
- Check every implemented app through its Dock entry and every drawer page; test back-and-forth app switching, `workspace.navigate`, toast/banner/badge, secondary area and primary actions. Check light/dark via the avatar Theme submenu, sizing presets, and app-frame widths from 360px. Capture business-frame states and the full shell; distinguish mock SDK behavior from live services. Use keyboard focus/press for React Aria controls when required, and unique button/dialog accessible names.
- Prefer Browser Use for the visible shell and business iframe, using its observed framePath and fresh refs. Confirm the actual committed URL and visible business content. Long content must be reviewed in overlapping scrolled viewport captures; a fullPage root-document image cannot expand the Workspace business iframe or its internal tables. Follow references/poc-review.md for coverage limits and recovery. Request original-quality, unannotated screenshots for acceptance; retain the verbatim PNG rather than relying on the display attachment. The bundled headless fallback supports real iframe actions through `frame: "iframe[data-primary-frame]"`; use it for full-shell navigation and business interactions. For other capture tools that cannot select inside an iframe, open the built URL with `?frame=app&app=<app-id>&page=<page-id>&scenario=<state>&scheme=light|dark`. This renders the business page alone at the capture viewport width and initializes its review state/theme. It supplements full-shell navigation checks; it does not prove shell integration. Inside the shell, SDK navigation, theme propagation and the top toolbar remain authoritative.
- Build with the installed package manager's `run build`. The Vite configuration emits **`project/delivery/index.html` with relative assets** for the existing static POC Preview. Never record the uncompiled source `project/index.html`. Use the shared `references/poc-review.md` workflow: `review-poc.mjs dev` checks selected sessions on the existing Vite/HMR server without a build; `review-poc.mjs final --project <task-dir>/project --source <task-dir> --out <task-dir> --scope app` builds once and reuses one browser capture for DOM checks and the evidence ledger. The ledger must fingerprint both authored sources and built delivery assets. After final source changes, rebuild and refresh all affected evidence before handoff; do not hand off a stale build.
- Use the normal `synapse_design_poc_handoff` with entry `<task-dir>/project/delivery/index.html` and all built HTML/CSS/JS/assets in `files` (within the existing file-count limit). Retain the normal screenshot presentation and user choice to revise, keep the prototype, or proceed to Synapse canvas. A requested code prototype remains a prototype; choosing Cobalt alone does not authorize production changes or bypass route consent.
